TỔNG QUAN ĐỀ TÀI & MỤC TIÊU NGHIÊN CỨU

Học phần "Triển khai và quản trị hệ thống phần mềm" là học phần chuyên ngành trọng yếu thuộc chương trình đào tạo Cử nhân Khoa học Máy tính. Mục tiêu của học phần là trang bị cho sinh viên khả năng thiết kế, đóng gói, tự động hóa quy trình triển khai và quản trị hạ tầng phần mềm hiện đại theo tiêu chuẩn công nghiệp (DevOps).

Với Đề tài 38, em được giao nhiệm vụ triển khai hệ thống Quản lý Chi tiêu Cá nhân (Expense Tracker). Để đáp ứng chuẩn đầu ra khắt khe nhất của năm thứ 4, hệ thống không chỉ dừng lại ở một ứng dụng web thông thường mà đã được hoàn thiện với đầy đủ:

  • Tầng Ứng dụng (Web Application): Frontend React 18, Vite, Recharts; Backend Node.js Express theo mô hình 3 lớp phân quyền RBAC (Admin và User).
  • Tầng Dữ liệu (Database): PostgreSQL 16 kết hợp công cụ quản trị trực quan pgAdmin 4.
  • Tầng Cổng vào (Gateway): Nginx Reverse Proxy hỗ trợ cả HTTP (80) và HTTPS tự ký (443), tích hợp Rate Limiting và Security Headers.
  • Tầng Giám sát & Quản trị Log (Observability): Prometheus cào metrics từ /metrics, Grafana hiển thị bảng điều khiển, Loki + Promtail thu thập log định dạng JSON và truy vấn bằng LogQL.

BƯỚC 2: TRIỂN KHAI ỨNG DỤNG WEB & CSDL POSTGRESQL + PGADMIN

2.1. Kiến trúc nghiệp vụ Ứng dụng Web Quản lý Chi tiêu (Expense Tracker)

Ứng dụng được xây dựng theo kiến trúc Client-Server hiện đại, chia tách rõ ràng 3 phân lớp (3-Tier Architecture):

  • Frontend Layer (React 18 + Vite 5 + Tailwind CSS): Cung cấp giao diện Dashboard với các chỉ số tài chính KPI: Tổng số dư, Tổng thu, Tổng chi, Tỷ lệ tiết kiệm và Chỉ số Sức khỏe tài chính (Financial Health Score 0-100). Tích hợp đồ thị tròn Recharts Doughnut phân bổ chi tiêu và đồ thị cột Cash Flow Trend so sánh đối ứng giữa các tháng.
  • Backend Layer (Node.js + Express REST API): Cung cấp 29 endpoints nghiệp vụ xử lý giao dịch, phân loại danh mục, lập ngân sách chi tiêu và tự động kích hoạt cảnh báo khi chi tiêu chạm ngưỡng 80% hoặc vượt 100% hạn mức.
  • Xác thực & Phân quyền (Authentication & RBAC): Mã hóa mật khẩu bằng thuật toán PBKDF2 (100.000 vòng lặp HMAC-SHA512 với salt 16 bytes), cấp phát token JWT (JSON Web Token). Phân quyền chặt chẽ 2 cấp độ: ADMIN (quản lý người dùng, xem telemetry hệ thống) và USER (quản lý thu chi cá nhân).

BƯỚC 3: CẤU HÌNH NGINX REVERSE PROXY & HTTPS TỰ KÝ

Theo Mục 3: "Cấu hình Nginx làm reverse proxy (có HTTPS tự ký hoặc security headers cơ bản)". File cấu hình nginx/nginx.conf đã được thiết kế hoàn chỉnh làm Cổng vào duy nhất (API Gateway) cho toàn bộ hệ thống.

3.1. Định tuyến Dịch vụ (Reverse Proxy Routing)

  • location /: Chuyển tiếp tới container Frontend (React SPA) cổng 3000.
  • location /api/: Chuyển tiếp tới container Backend Node.js cổng 5000.
  • location /api/auth/: Tuyến xác thực áp dụng Rate Limiting chặt chẽ.
  • location /metrics: Chuyển tiếp dữ liệu giám sát tới Prometheus.

3.2. Cấu hình HTTPS với Chứng chỉ SSL Tự ký (Self-Signed Certificate)

Chứng chỉ số RSA 2048-bit được tạo tự động bằng OpenSSL với thông tin định danh sinh viên: /C=VN/ST=ThaiNguyen/L=ThaiNguyen/O=ICTU/OU=KHMT/CN=localhost. 

server {
    listen 443 ssl;
    server_name localhost;

    ssl_certificate     /etc/nginx/ssl/server.crt;
    ssl_certificate_key /etc/nginx/ssl/server.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    ...
}

BƯỚC 4: GIÁM SÁT HỆ THỐNG VỚI PROMETHEUS & GRAFANA

Theo Mục 4: "Tích hợp Prometheus + Grafana để giám sát container, web server và database". Hệ thống đã triển khai giải pháp giám sát thời gian thực toàn diện.

4.1. Tích hợp Exporter Backend Node.js qua thư viện prom-client

Tại server/src/utils/metrics.js, hệ thống đã khai báo và thu thập 3 nhóm metrics tiêu chuẩn:

  • http_requests_total: Counter đếm tổng số lượt request phân loại theo method, route, status_code.
  • http_request_duration_seconds: Histogram đo độ trễ xử lý (Latency) với các bucket từ 5ms đến 5 giây.
  • nodejs_heap_size_used_bytes: Gauge đo dung lượng RAM mà tiến trình Node.js đang tiêu thụ.
  • Dữ liệu được phơi bày qua endpoint chuẩn: GET /metrics (Mã phản hồi HTTP 200).

4.2. Cấu hình Prometheus Scraper (prometheus.yml)

Prometheus được cấu hình tự động cào metrics từ container Backend định kỳ mỗi 5 giây: 

global:
  scrape_interval: 5s
  evaluation_interval: 5s

scrape_configs:
  - job_name: 'expense-tracker-backend'
    metrics_path: '/metrics'
    static_configs:
      - targets: ['backend:5000']

4.3. Bảng điều khiển Grafana Dashboard Tự động (Provisioning)

Grafana chạy tại cổng 3001 (Tài khoản: admin / admin). Thư mục monitoring/grafana/provisioning/ tự động nạp Datasource Prometheus và Dashboard JSON gồm 6 biểu đồ chuyên nghiệp:

BƯỚC 5: QUẢN TRỊ LOG TẬP TRUNG LOKI + PROMTAIL & LOGQL

Theo Mục 5: "Triển khai hệ thống log tập trung Loki + Promtail, truy vấn log bằng LogQL (ít nhất 2–3 query)".

5.1. Kiến trúc Thu thập & Lưu trữ Log Tập trung

Khác với cách xem file log truyền thống rời rạc, hệ thống sử dụng kiến trúc gom log hiện đại:

  • Nginx: Ghi log truy cập dưới định dạng cấu trúc JSON Analytics chứa đầy đủ: time_local, client_ip, request, status, request_time, upstream_response_time.
  • Promtail: Đóng vai trò Log Shipper, đọc liên tục các file log trong /var/log/nginx/ và đẩy về Loki qua cổng 3100.
  • Grafana Loki: Lưu trữ log theo dạng Time-series đánh chỉ mục theo nhãn (Labels: job="nginx", service="reverse-proxy").

5.2. Các câu lệnh truy vấn LogQL thực tế phục vụ vấn đáp thi cử

Dưới đây là 4 câu lệnh truy vấn LogQL mẫu đã được kiểm nghiệm, sẵn sàng thực thi trực tiếp trên giao diện Grafana Explore:

Query 1: Xem toàn bộ luồng Access Log thời gian thực của Nginx

{job="nginx"}

→ Hiển thị toàn bộ nhật ký truy cập từ người dùng và trình duyệt gửi tới hệ thống.

Query 2: Lọc các truy vấn phát sinh lỗi HTTP 4xx hoặc 5xx

{job="nginx"} | json | status >= 400

→ Trích xuất tức thì các yêu cầu bị từ chối hoặc lỗi máy chủ để quản trị viên xử lý sự cố.

Query 3: Tìm kiếm các vết lỗi Exception trong Backend Express

{job="backend"} |= "error"

→ Lọc nhanh các bản ghi chứa từ khóa "error" hoặc "fail" trong luồng xử lý Node.js.

Query 4: Tính toán tần suất gọi vào API Đăng nhập (Auth Rate)

rate({job="nginx"} |= "/api/auth/login" [1m])

→ Vẽ biểu đồ trực tiếp tần suất người dùng đăng nhập để phát hiện các đợt tấn công dò mật khẩu.

BƯỚC 6: ÁP DỤNG TOÀN DIỆN CÁC BIỆN PHÁP GIA CỐ BẢO MẬT (HARDENING)

Theo Mục 6: "Áp dụng các biện pháp hardening: non-root container, network isolation, mật khẩu mạnh, hạn chế quyền, security headers Nginx, v.v."

6.1. Gia cố cấp độ Container (Docker Non-root Execution)

Mặc định, các container chạy dưới quyền root (UID 0), tiềm ẩn nguy cơ nghiêm trọng nếu mã nguồn bị khai thác chiếm quyền điều khiển. Trong server/Dockerfile, em đã áp dụng nguyên tắc đặc quyền tối thiểu (Least Privilege): 

# Phân quyền thư mục và chuyển sang người dùng không đặc quyền
RUN chown -R node:node /app
USER node

Tiến trình Backend Node.js chỉ chạy với quyền user node, triệt tiêu nguy cơ leo thang đặc quyền ra máy chủ vật lý.

6.2. Phân tách mạng ảo (Network Isolation)

Tất cả 8 dịch vụ đều nằm trong mạng nội bộ expense_net (bridge driver). CSDL PostgreSQL (5432) và pgAdmin chỉ giao tiếp nội bộ trong cụm Docker, người dùng bên ngoài Internet bắt buộc phải đi qua Nginx Reverse Proxy tại cổng 80/443.

6.3. Chính sách Mật khẩu mạnh & Mã hóa

  • Mật khẩu người dùng: Thuật toán băm PBKDF2 với 100.000 vòng lặp HMAC-SHA512 + muối 16 bytes.

6.4. Phân quyền Volume chỉ đọc (Read-Only Volume Mounts)

Các file cấu hình nhạy cảm được gắn cờ :ro trong docker-compose.yml: ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro, ./postgres/init.sql:...:ro, ./monitoring/prometheus/...:ro. Container không có quyền sửa đổi file cấu hình hệ thống.

6.5. Gia cố hệ điều hành Linux Host (Tường lửa UFW & Kernel Hardening)

# 1. Cấu hình tường lửa UFW
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp
sudo ufw enable

# 2. Chống tấn công SYN Flood và IP Spoofing trong /etc/sysctl.conf
net.ipv4.tcp_syncookies = 1
net.ipv4.conf.all.rp_filter = 1
